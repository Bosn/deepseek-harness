# Agent Note: 为请求大小与停滞流恢复设置边界

Status: implemented

[English](2026-08-21-request-size-timeout-recovery.md) | 中文

## 问题

normal 提供方策略可能让耗时差异很大的失败共享同一份重试预算。pi-ai 流空闲超时可能等待五分钟才报告 `TIMEOUT`；如果该 code 可以耗尽默认的五次重试预算，一个轮次可能在请求完全不变的循环里停留半小时以上。大请求会进一步恶化问题：当超时来自上传侧停滞时，通用重试只会原样重发同一个请求体，不会进行任何修复。HTTP 413 具有相同的结构性要求；若不显式解析，pi-ai 展平的非 2xx 错误会丢失请求大小恢复和按提供方区分带 quota 措辞 429 所需的状态码。

请求大小恢复还必须约束它自己的摘要调用。用同样超大的回放来替换超大对话，只会把网关拒绝转移进压缩；如果摘要器省略较早消息，却在持久表层替换这些消息，就会在没有摘要的情况下丢失模型可见历史。

## 决策

- Pi-ai 从 SDK 展平后的错误文本提取显式 HTTP 状态码，包括 vendored pi-messages 的行首 `NNN Reason Phrase:` 格式，例如 `413 Payload Too Large:` 和 `429 Too Many Requests:`，并记录到 `LlmFailure`。普通 HTTP 429 映射为 `RATE_LIMIT`；quota 措辞保持 `QUOTA`，仅当显式 429 出现在已解析 `quotaWorded429IsRateLimit` 为 true 的路由上时例外。内建 qwen token-plan 路由默认开启该字段，OpenAI 与未知自定义路由默认关闭。显式状态优先；SDK 展平文本没有状态时，只有严格识别出的请求体或 payload 长度上限措辞会被规范化为状态 413。HTTP 413 与这些已识别的请求体上限失败映射为 `CONTEXT_WINDOW_EXCEEDED`，没有状态的语义上下文溢出仍不携带状态。直连 DeepSeek 的每个 HTTP 非 2xx 失败，都会记录请求转换与图片 offload 后精确的 UTF-8 序列化 payload 字节数。如果序列化已完成，流空闲 `TIMEOUT` 也会记录该数值；转换期间超时则没有估算。Pi-ai 会为 SDK 终态 `done`/`error` 事件产生的每个失败，以及转换后由适配器生成的 `TIMEOUT`/`ABORTED`，记录转换后 context 的估算；转换前失败与其它直接抛出的 SDK 错误不保证携带该估算。SDK 只对成功响应调用 response hook，因此 pi-ai 不会声称拥有实际不可用的非 2xx 响应头、`Retry-After` 或请求 ID。
- normal 重试策略增加 `maxRetriesByCode`，参与校验、不可变解析与规范策略键。省略默认值为 `{ TIMEOUT: 1 }`；未列出的 code 继续使用共享 `maxRetries` 上限，显式 always 策略不设逐代码上限。
- 两种重试 mode 都会在安排重复请求前，把符合条件的失败委托给下游恢复，并优先采用专用 `{ kind: 'retry' }` 决定。如果下游持久替换表层但未授权另一请求，两种 mode 都会抑制回退，避免通用重试与已经失去请求归属或遇到竞争事务的专用修复并发。除此之外，normal 通用重试只在没有下游监听器修复请求时运行，预算耗尽路径在这一次委托后直接返回。
- 压缩把 HTTP 413 视为请求大小失败；只有适配器转换后的估算（缺省时使用表层请求估算）达到 `timeoutRecoveryBytes`（默认 512 KiB）时，`TIMEOUT` 才使用相同路径。这避免已 offload 的图片字节把无关超时变成请求大小恢复。回退字节估算器会计价内置内容的转义 JSON 与 framing。每个正数的已确认 413 预算都会约束当次 summarizer；低于 64 KiB 主动实用 floor 的值不会持久化。两条恢复路径都会绕过常规压力与保留尾部策略，并使用既有 `maxOverflowRetries` 预算。完整替换或部分持久进展之后，只有原 request-error 的轮次与步骤仍开放、且没有活动持久压缩锁时，才会允许重试。所抛的 `busy` 失败还会额外阻止使用部分进展重试；其他未通过准备状态检查的情况会保留提供方失败，避免与竞争摘要并发。请求大小恢复会在持久推进后，按 `learnedByteSafetyRatio`（默认 `0.75`）为对应 agent 与精确提供方／模型路由发布主动字节预算；语义上下文溢出不会学习。
- `summarizationInputBytes`（默认 512 KiB）限制自动压力、显式范围与 `compactNow()` 入口生成的完整摘要请求：路由头、回放消息与固定指令。`maxRequestBytes` 也会限制该请求。顶层默认值或精确模型覆盖完成继承后，`resolveConfig` 会拒绝无法在分派字节估算器下容纳一条最小回放消息与固定指令的有效 `min(summarizationInputBytes, maxRequestBytes)`。在切分整条消息之前，引擎会按请求顺序应用共享图片策略，逐张替换最旧图片，并在每次替换后重新检查完整的请求头、post-offload 消息与指令估算。随后，超大范围会通过较早的平衡事务压缩，直到每个请求都可装入上限。每个新检查点都会进入下一次有界处理，因此完整替换会收敛为一个检查点，而不会累积各分区摘要。每个检查点都必须装入下一次完整摘要请求，并且同时严格缩小精确 post-offload 回放的路由定价 token 与估算字节；图片 offload 不会放宽任一比较。一次分层处理最多允许入口所选每个表层节点触发一次提供方调用。分层操作开始时，引擎会捕获其数字或 `null` 的轮次归属。在每个具体事务同步追加 `compaction/start` 紧前，它都会重新读取持久锁、解析当前归属，并要求它与初始归属一致；检查与追加之间没有 `await`。竞争锁、轮次关闭或轮次被替换会在产生新的开始标记、摘要或替换之前停止整个分层处理。切分会保留 tool-call/result 配对；每条被替换消息都进入某个有界摘要输入；无法拆分且超限的单元会在提供方调用前失败。

## 曾考虑的替代方案

**提高或复用共享重试次数。** 不予采纳，因为请求次数不是时间边界：五个五分钟空闲期限在退避前就可能占住轮次至少 25 分钟，而且未变化的大请求没有得到修复。

**把所有 TIMEOUT 都归因于请求大小。** 不予采纳，因为小请求也可能因普通传输或提供方故障而超时。`timeoutRecoveryBytes` 把启发式限制在足够大、上传侧压力确有可能的转换后请求体。

**截断摘要器回放但替换完整范围。** 不予采纳，因为持久检查点会声称摘要了模型从未收到的消息。

**通过通用策略重试 HTTP 413。** 不予采纳，因为相同请求体无法通过同一字节上限；只有重建请求才可能取得进展。

## 验证

解析器与重试测试覆盖校验、冻结、顶层与精确模型摘要输入下限、策略键分离、TIMEOUT 默认只重试一次、显式下游重试优先级，以及 normal/always 的持久替换 veto。真实 Loader 组合通过模拟的 OpenAI 兼容 HTTP 服务路由 pi-ai：显式开启的自定义 qwen 路由会观测到带状态码 429 的 `RATE_LIMIT`，等待配置的冷却时间，并在下一次尝试成功；OpenAI 路由则把同样带 quota 措辞的 429 保留为终态 `QUOTA`，且不重试。适配器测试覆盖直连 DeepSeek 非 2xx 状态映射及其精确序列化请求估算、Vision HTTP 413 与空闲超时、pi-ai 显式状态提取（包括行首 reason phrase）、对严格识别的展平请求体上限推导 413、语义溢出不携带状态的负对照、代表性的转换后 context 估算、按路由区分的 quota 措辞 429 分类、终态非 429 quota、请求局部超时中止，以及并发请求隔离。压缩测试覆盖 HTTP 413、大小请求 TIMEOUT 分流、精确路由学习预算、有界自动与手动入口、平衡的分层请求、工具配对边界、不可拆超限失败、完整 envelope 图片 offload、每个检查点严格缩小 post-offload 路由 token 与字节、多字节检查点、逐入口节点事务上限，以及提供方调用前对完整请求上限的强制执行。一个组装后的请求错误用例携带低于两 MB 单张持久图片估算的 post-offload 413 估算，摘要足够多的 post-offload 历史以产生严格更小的检查点，并让适配器在成功前用同一字节上限重检重建请求。测试固定了正常的双事务路径与嵌套的三事务路径；首个事务闭合后，竞争锁、归属轮次关闭或轮次被替换，都会在产生新的 `compaction/start`、摘要或表层替换之前拒绝后续事务。失败请求生命周期测试会关闭或替换原轮次与步骤，并在部分或成功恢复后引入竞争锁；每种情况都会保留提供方失败，而不发起另一次对话请求。一个组装后的大请求 TIMEOUT 用例验证通用重试无法绕过成功恢复的锁检查。统一的 `snapshots/session/compaction-recovery` 无密钥场景覆盖组装后的 HTTP 413 恢复，`apps/cli/tests/profiles/headless/tests/expected/provider-retry` 则覆盖瞬态重试。

## 后果

默认 normal 路由在超时后最多执行一次未变化的通用重试，而超时的大请求会先获得一次有界压缩恢复机会。HTTP 413 会重建更小的请求，而不是终止会话或重复被拒请求体。请求大小恢复可能在大请求超时并非由请求体大小引起时做出保守压缩；运维方可以提高 `timeoutRecoveryBytes`、调整 `learnedByteSafetyRatio`，或用 `maxOverflowRetries: 0` 禁用失败请求恢复。由于 SDK 不会在非 2xx 失败上暴露响应头，pi-ai 路由只使用配置的 429 冷却时间，不使用提供方响应头提示。
