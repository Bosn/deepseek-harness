# Agent Note: 为请求大小与停滞流恢复设置边界

Status: implemented

[English](2026-08-21-request-size-timeout-recovery.md) | 中文

## 问题

normal 提供方策略可能让耗时差异很大的失败共享同一份重试预算。pi-ai 流空闲超时可能等待五分钟才报告 `TIMEOUT`；如果该 code 可以耗尽默认的五次重试预算，一个轮次可能在请求完全不变的循环里停留半小时以上。大请求会进一步恶化问题：当超时来自上传侧停滞时，通用重试只会原样重发同一个请求体，不会进行任何修复。HTTP 413 具有相同的结构性要求；若不显式解析，pi-ai 展平的非 2xx 错误会丢失状态码，而 quota 措辞可能在状态码取得优先权之前把 HTTP 429 归类为终态 `QUOTA`。

请求大小恢复还必须约束它自己的摘要调用。用同样超大的回放来替换超大对话，只会把网关拒绝转移进压缩；如果摘要器省略较早消息，却在持久表层替换这些消息，就会在没有摘要的情况下丢失模型可见历史。

## 决策

- Pi-ai 从 SDK 展平后的错误文本提取显式 HTTP 状态码，并记录到 `LlmFailure`。HTTP 429 的优先级高于 quota 措辞并映射为 `RATE_LIMIT`；非 429 quota 仍为 `QUOTA`。HTTP 413 与请求体上限措辞映射为 `CONTEXT_WINDOW_EXCEEDED`。Pi-ai 与直连 DeepSeek 的超时失败都会在各自请求转换与图片 offload 后记录 UTF-8 字节估算。SDK 只对成功响应调用 response hook，因此 pi-ai 不会声称拥有实际不可用的非 2xx 响应头、`Retry-After` 或请求 ID。
- normal 重试策略增加 `maxRetriesByCode`，参与校验、不可变解析与规范策略键。省略默认值为 `{ TIMEOUT: 1 }`；未列出的 code 继续使用共享 `maxRetries` 上限，显式 always 策略不设逐代码上限。
- normal 通用重试在安排重复请求前，会把符合条件的失败委托给下游恢复。专用 `{ kind: 'retry' }` 决定优先；只有没有下游监听器修复请求时才执行通用重试，预算耗尽路径在这一次委托后直接返回。
- 压缩把 HTTP 413 视为请求大小失败；只有适配器转换后的估算（缺省时使用表层请求估算）达到 `timeoutRecoveryBytes`（默认 512 KiB）时，`TIMEOUT` 才使用相同路径。这避免已 offload 的图片字节把无关超时变成请求大小恢复。回退字节估算器会计价内置内容的转义 JSON 与 framing。每个正数的已确认 413 预算都会约束当次 summarizer；低于 64 KiB 主动实用 floor 的值不会持久化。两条恢复路径都会绕过常规压力与保留尾部策略，使用既有 `maxOverflowRetries` 预算，并且只在持久表层替换后重试。请求大小恢复只有在持久推进后才按 `learnedByteSafetyRatio`（默认 `0.75`）为对应 agent 与精确提供方／模型路由发布主动字节预算；语义上下文溢出不会学习。
- `summarizationInputBytes`（默认 512 KiB）限制自动压力、显式范围与 `compactNow()` 入口生成的完整摘要请求：路由头、回放消息与固定指令。超大范围先通过较早的平衡事务压缩，直到每个请求都可装入上限。每个新检查点都会进入下一次有界处理，因此完整替换会收敛为一个检查点，而不会累积各分区摘要。切分会保留 tool-call/result 配对；每条被替换消息都进入某个有界摘要输入；无法拆分且超限的单元会在提供方调用前失败。

## 曾考虑的替代方案

**提高或复用共享重试次数。** 不予采纳，因为请求次数不是时间边界：五个五分钟空闲期限在退避前就可能占住轮次至少 25 分钟，而且未变化的大请求没有得到修复。

**把所有 TIMEOUT 都归因于请求大小。** 不予采纳，因为小请求也可能因普通传输或提供方故障而超时。`timeoutRecoveryBytes` 把启发式限制在足够大、上传侧压力确有可能的转换后请求体。

**截断摘要器回放但替换完整范围。** 不予采纳，因为持久检查点会声称摘要了模型从未收到的消息。

**通过通用策略重试 HTTP 413。** 不予采纳，因为相同请求体无法通过同一字节上限；只有重建请求才可能取得进展。

## 验证

解析器与重试测试覆盖校验、冻结、策略键分离、TIMEOUT 默认只重试一次，以及下游恢复优先级。真实 Loader 组合通过模拟的 OpenAI 兼容 HTTP 服务路由 pi-ai：服务先返回带 quota 措辞的 429，系统观测到带状态码 429 的 `RATE_LIMIT`，等待配置的冷却时间，并在下一次尝试成功。适配器测试覆盖显式 413/429/5xx 状态提取、终态非 429 quota、请求局部超时中止与并发请求隔离。压缩测试覆盖 HTTP 413、大小请求 TIMEOUT 分流、精确路由学习预算、有界自动与手动入口、平衡的分层请求、工具配对边界、不可拆超限失败，以及提供方调用前对完整请求上限的强制执行。无密钥 headless 与 ACP 快照覆盖组装后的 HTTP 413 恢复和瞬态重试。

## 后果

默认 normal 路由在超时后最多执行一次未变化的通用重试，而超时的大请求会先获得一次有界压缩恢复机会。HTTP 413 会重建更小的请求，而不是终止会话或重复被拒请求体。请求大小恢复可能在大请求超时并非由请求体大小引起时做出保守压缩；运维方可以提高 `timeoutRecoveryBytes`、调整 `learnedByteSafetyRatio`，或用 `maxOverflowRetries: 0` 禁用失败请求恢复。由于 SDK 不会在非 2xx 失败上暴露响应头，pi-ai 路由只使用配置的 429 冷却时间，不使用提供方响应头提示。
