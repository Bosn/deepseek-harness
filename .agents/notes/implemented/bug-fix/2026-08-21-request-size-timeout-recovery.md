# Agent Note: Bound request-size and stalled-stream recovery

Status: implemented

English | [中文](2026-08-21-request-size-timeout-recovery.zh.md)

## Problem

A normal provider policy can assign one shared retry budget to failures with very different time costs. A pi-ai stream idle timeout may consume five minutes before it reports `TIMEOUT`; allowing that code to consume the full default five-retry budget can keep one turn in an unchanged request loop for more than half an hour. A large request makes this worse when the timeout is an upload-side stall: generic retry resends the same envelope without any repair. HTTP 413 has the same structural requirement, but without explicit parsing pi-ai's flattened non-2xx error loses the status needed for request-size recovery and provider-specific quota-worded 429 classification.

Request-size recovery must also bound its own summarizer call. Replacing an oversized conversation through one equally oversized replay merely moves the gateway rejection into compaction; omitting older messages from the summarizer while replacing them durably would lose model-visible history without summarizing it.

## Decision

- Pi-ai extracts explicit HTTP status from the SDK's flattened error text, including vendored pi-messages' line-leading `NNN Reason Phrase:` form such as `413 Payload Too Large:` and `429 Too Many Requests:`, and records it on `LlmFailure`. Plain HTTP 429 maps to `RATE_LIMIT`; quota wording remains `QUOTA` unless an explicit 429 arrives on a route whose resolved `quotaWorded429IsRateLimit` is true. The built-in qwen token-plan routes default that field on, while OpenAI and unknown custom routes default it off. Explicit status wins; when flattened SDK text carries none, narrowly recognized request-body or payload length-limit wording is normalized to status 413. HTTP 413 and those recognized body-cap failures map to `CONTEXT_WINDOW_EXCEEDED`, while semantic context overflow without a status remains status-less. Every direct DeepSeek HTTP non-2xx failure records the exact UTF-8 serialized payload size after request conversion and image offload. Its stream-idle `TIMEOUT` records the same fact when serialization completed; a timeout during conversion has no estimate. Pi-ai records its converted-context estimate on every failure produced from a terminal SDK `done`/`error` event and on adapter-generated `TIMEOUT`/`ABORTED` after conversion; failures before conversion and other thrown SDK errors have no estimate guarantee. The SDK invokes its response hook only for successful responses, so pi-ai does not claim unavailable non-2xx headers, `Retry-After`, or request ids.
- Normal retry policy has `maxRetriesByCode`, included in validation, immutable resolution, and the canonical policy key. The omission default is `{ TIMEOUT: 1 }`; unlisted codes retain the shared `maxRetries` limit, and explicit always policy has no per-code cap.
- Both retry modes delegate eligible failures to downstream recovery before scheduling a repetition, and a specialized `{ kind: 'retry' }` decision wins. If downstream durably replaces the surface without authorizing another request, both modes suppress fallback so generic retry cannot race a specialized repair that lost request ownership or encountered a competing transaction. Normal generic retry otherwise runs only when no downstream listener repairs the request, and exhausted paths return after that single delegation.
- Compaction treats HTTP 413 as request-size failure and treats `TIMEOUT` the same way only when the adapter-converted estimate, or the surfaced-request fallback, reaches `timeoutRecoveryBytes` (default 512 KiB). This prevents offloaded image bytes from turning an unrelated timeout into request-size recovery. The fallback byte estimator prices escaped JSON and framing for built-in content. Every positive confirmed-413 budget constrains its current summarizer; values below the 64 KiB proactive usefulness floor are not persisted. Both recovery paths bypass ordinary pressure and retained-tail policy and use the existing `maxOverflowRetries` budget. After a completed replacement or partial durable progress, retry is authorized only if the original request-error turn and step remain open and no durable compaction lock is active. A thrown `busy` failure additionally blocks partial-progress retry; otherwise a failed readiness check preserves the provider failure instead of racing a competing summary. Request-size recovery publishes a proactive byte budget at `learnedByteSafetyRatio` (default `0.75`) after durable progress, scoped to that agent and exact provider/model route; semantic context overflow does not.
- `summarizationInputBytes` (default 512 KiB) caps the complete summarizer request from automatic pressure, explicit-region, and `compactNow()` entry points: routed header, replayed messages, and fixed instruction. `maxRequestBytes` also constrains that request. After top-level defaults or an exact-model override are inherited, `resolveConfig` rejects an effective `min(summarizationInputBytes, maxRequestBytes)` that cannot hold one minimal replay message plus the fixed instruction under the dispatch byte estimator. Before partitioning whole messages, the engine applies the shared request-order image policy one oldest image at a time and rechecks the complete header-plus-post-offload-messages-plus-instruction estimate after each replacement. Oversized ranges then compact through earlier balanced transactions until every request fits. Each generated checkpoint enters the next bounded pass, so the complete replacement converges to one checkpoint instead of accumulating partition summaries. Every checkpoint must fit the next complete summarizer request and strictly shrink the exact post-offload replay in both route-priced tokens and estimated bytes; image offload does not relax either comparison. One hierarchy permits at most one provider call per surface node selected at entry. At the start of that hierarchy, the engine captures its numeric-or-null turn owner. Immediately before synchronously appending `compaction/start` for every concrete transaction, it rereads the durable lock, resolves the current owner, and requires it to match the initial owner; the check and append have no intervening `await`. A competing lock or closed/replaced turn stops the hierarchy before another start, summary, or replacement. Partitions preserve tool-call/result pairs, every replaced message is represented in a bounded summarizer input, and an indivisible over-cap unit fails before provider dispatch.

## Alternatives considered

**Raise or reuse the shared retry count.** Rejected because request count is not a time bound: five five-minute idle deadlines can still hold a turn for at least 25 minutes before backoff, and an unchanged large envelope receives no repair.

**Classify every TIMEOUT as request size.** Rejected because small requests can time out from ordinary transport or provider outages. `timeoutRecoveryBytes` confines the heuristic to converted envelopes large enough for upload-side pressure to be plausible.

**Truncate the summarizer replay but replace the full range.** Rejected because a durable checkpoint would then claim to summarize messages the model never received.

**Retry HTTP 413 through generic policy.** Rejected because the identical body cannot pass the same byte cap; only a rebuilt request can make progress.

## Verification

Resolver and retry tests cover validation, freezing, top-level and exact-model summarization-input minima, policy-key separation, one-retry TIMEOUT defaults, explicit downstream-retry precedence, and the normal/always durable-replacement veto. A real Loader composition routes pi-ai through a mock OpenAI-compatible HTTP server: an opted-in custom qwen route observes `RATE_LIMIT` with status 429, waits the configured cooldown, and succeeds on the rebuilt attempt, while an OpenAI route preserves the same quota-worded 429 as terminal `QUOTA` without retrying. Adapter tests cover direct DeepSeek non-2xx status mapping with exact serialized request estimates, Vision HTTP 413 and idle timeout, pi-ai explicit status extraction including line-leading reason phrases, inferred 413 for narrowly recognized flattened request-body limits, a semantic-overflow no-status negative control, representative converted-context estimates, route-specific quota-worded 429 classification, terminal non-429 quota, request-local timeout abort, and concurrent-request isolation. Compaction tests cover HTTP 413, large and small TIMEOUT paths, exact-route learned budgets, bounded automatic and manual entry points, balanced hierarchical requests, tool-pair boundaries, indivisible oversize failure, full-envelope image offload, strict post-offload route-token and byte shrink for every checkpoint, multibyte checkpoints, the per-entry-node transaction limit, and complete-request cap enforcement before provider dispatch. One assembled request-error case carries a post-offload 413 estimate below a two-megabyte durable single-image estimate, summarizes enough post-offload history to produce a strictly smaller checkpoint, and makes the adapter recheck the rebuilt request against the same byte cap before succeeding. Normal two-transaction and nested three-transaction paths are pinned; after the first transaction closes, a competing lock, a closed owner turn, or a replacement turn rejects before another `compaction/start`, summary, or surface replacement. Failed-request lifecycle tests close or replace the original turn and step and race a competing lock after partial or successful recovery; each preserves the provider failure without another conversation request. An assembled large-TIMEOUT case verifies that generic retry cannot bypass the successful-recovery lock guard. The unified `snapshots/session/compaction-recovery` keyless scenario exercises assembled HTTP 413 recovery, while `apps/cli/tests/profiles/headless/tests/expected/provider-retry` exercises transient retry.

## Consequences

A default normal route makes at most one unchanged generic retry after a timeout, while a large timed-out request first receives one bounded compaction recovery opportunity. HTTP 413 reconstructs a smaller request rather than ending the session or repeating the rejected body. Request-size recovery may compact conservatively after a large timeout that was not caused by body size; operators can raise `timeoutRecoveryBytes`, change `learnedByteSafetyRatio`, or disable failed-request recovery with `maxOverflowRetries: 0`. Pi-ai routes use configured 429 cooldowns without provider response-header hints because the SDK does not expose those headers on non-2xx failures.
